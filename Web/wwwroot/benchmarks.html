Lightning SPP / Benchmarks
Performance

Measured, not marketed.

Performance depends on hardware, input size, and configuration. We publish methodology and reproducible commands rather than universal latency claims.

Numbers below are measured, not guaranteed. Any benchmark result is only meaningful with its hardware spec, dataset, configuration and repetition count attached — the one example further down this page is a single developer machine, not a universal promise. Run the commands below on your own target hardware for numbers that apply to your deployment.

Run the benchmark yourself

dotnet build
dotnet run -- speed
dotnet run -- pipeline document.pdf
WWWMMM_STIGMA_LEVEL=3 dotnet run -- pipeline document.pdf   # lightning profile
WWWMMM_STIGMA_LEVEL=1 dotnet run -- pipeline document.pdf   # quality profile

The xUnit suite also includes golden-output and performance-gate tests that run against every change:

dotnet test ./Tests/LightningSPP.Tests/LightningSPP.Tests.csproj

What a valid benchmark report includes

Hardware

CPU, RAM, disk type, OS and .NET runtime version used for the run.

Dataset

File types, sizes, and count of documents processed.

Configuration

The Stigma profile (WWWMMM_STIGMA_LEVEL) and any non-default settings.

Repetitions

Number of runs, warm-up handling, and reported variance (not just a single best-case number).

Why this matters

Lightning SPP's own documentation intentionally avoids restating latency targets as guarantees — they are benchmark objectives, not universal promises. See SUMMARY.md and REAL_PROCESSING.md for the current state of real (non-simulated) processing.
