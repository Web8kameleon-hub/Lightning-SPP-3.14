Lightning SPP / Benchmarks
Performance

Measured, not marketed.

Performance depends on hardware, input size, and configuration. We publish methodology and reproducible commands rather than universal latency claims.

Numbers below are measured, not guaranteed. Any benchmark result is only meaningful with its hardware spec, dataset, configuration and repetition count attached — the one example further down this page is a single developer machine, not a universal promise. Run the commands below on your own target hardware for numbers that apply to your deployment.

Document workloads: what still needs measurement

The engine measurements below are not end-to-end document benchmarks. No customer workload results or cross-plan performance comparison are published in this section.

Scanned report

Use a real multipage PDF. Record page count, dimensions, input hash and size, rendering time, processing time, total elapsed time and output size. Re-render the downloaded PDF and check every page.

Image batch

Use a fixed collection of representative scans. Record formats, dimensions, file count, successful and rejected files, peak memory, throughput and output quality against the originals.

Run the same dataset separately for every applicable product plan and processing profile. Record the exact plan name and enforced limits; a commercial tier and a Stigma processing profile are different variables. Include warm-up, repetitions, median and p95, failures, runtime, hardware and commit. Publish raw records with the summary.

Run the benchmark yourself

dotnet build
dotnet run -- speed
dotnet run -- pipeline document.pdf
WWWMMM_STIGMA_LEVEL=3 dotnet run -- pipeline document.pdf   # lightning profile
WWWMMM_STIGMA_LEVEL=1 dotnet run -- pipeline document.pdf   # quality profile

The xUnit suite also includes golden-output and performance-gate tests that run against every change:

dotnet test ./Tests/LightningSPP.Tests/LightningSPP.Tests.csproj

If a field was not captured during a run, it should remain undisclosed rather than inferred later.

What we will not claim without evidence

Lightning-only measurements do not establish superiority over another product. Comparative statements such as faster, cheaper, or higher quality require equivalent inputs, feature parity, product versions, regional pricing, timestamps and raw results for every product being compared.

No fake evidence: engineering targets are not customer guarantees, CI gates are not benchmark results, and a successful test does not establish performance on hardware that was not measured.

What a valid benchmark report includes

Hardware

CPU, RAM, disk type, OS and .NET runtime version used for the run.

Dataset

File types, sizes, and count of documents processed.

Configuration

The Stigma profile (WWWMMM_STIGMA_LEVEL) and any non-default settings.

Repetitions

Number of runs, warm-up handling, and reported variance (not just a single best-case number).

Why this matters

Lightning SPP's own documentation intentionally avoids restating latency targets as guarantees — they are benchmark objectives, not universal promises. See SUMMARY.md and REAL_PROCESSING.md for the current state of real (non-simulated) processing.
